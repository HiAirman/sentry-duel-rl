哨兵大战 GRU 记忆探索

给哨兵策略网络加一层循环记忆,让它记住视野外的信息。目标是对阵四个指定对手 胜率均 ≥ 0.70 —— 达标了。但消融实验显示:记忆本身的贡献落在测量噪声里 —— v2.3 上补做的这一次是三次里第一个符号朝正的(+0.0250),仍然测不准(§7.4)。

目标(用户原话):增加记忆机制,使用 RNN / Transformer 架构做决策,不断探索和训练, 直到对阵 rl_v5 / rl_VG_v0.2 / rl_best040 / rl_VG_v1.0 训练胜率均 ≥ 0.70,然后打包。

目标已达成 4 / 4 对手过线 交付物 rl_VG_v2.3 验证 2 个独立种子 × 400 局 最紧一格 rl_v5 = 0.785

§2

架构与设计

2.1结构:编码器不动,记忆做成零初始化残差

a_t  = Encoder(obs_t)            # 与 rl_VG_v1.0 的编码器逐层同构(428→512→512→512)
h_t  = GRU_128(a_t, h_{t-1})     # 新增
feat = a_t + P·h_t + bP          # P、bP 零初始化
π_t  = W3·feat + b3     V_t = Wv·feat + bv

P = bP = 0 让训练第一步的整个前向逐位等于 rl_VG_v1.0 (tests/test_rnn_policy.py 逐位断言)。这一条是整个设计里最重要的决定:

  • 最差的情况是"记忆层学成不用它",而不是"一上来就把一个已经很强的策略弄坏";
  • 反过来,如果把 GRU 输出直接当 feat,三个头面对的是全新输入分布, v1.0 学到的策略头当堂作废 —— 而这一轮的目标恰恰是"打赢 v1.0",从作废的策略起步是最差的开局。

gru_hidden 取 128 而不是 512:GRU 参数是 3*(I·G + G·G) 量级, 512 会多出约 6.3MB,而权重头已经 10.3MB(评测服务单文件上限 8MB,靠分片绕开,但总量仍要克制)。

2.2训练:截断 BPTT(R2D2 stored-state)

循环网络不能沿用 ppo.py 的"把单个时间步打乱成 minibatch" —— 同一批里混着来自不同时刻、不同局的步,隐状态传不下去,记忆层永远学不到跨步依赖, 而且不报错、不崩,只是"加了 RNN 但没变强"。monet/models/ppo_seq.py 改成:

  1. 按 done 把 rollout 切成局;段绝不允许跨局 (跨局会把上一局末尾的隐状态带进新的一局,而新一局 h 必须归零);
  2. 每局再切成定长段(seg_len=32;一局约 54 个决策点,所以多数局只被切 2 段);
  3. minibatch 由若干整段组成;每段的初始隐状态用采样时存下来的那个 (= 段起点进入时的 h,天然 detached),这就是截断点;
  4. 段尾不足一整段的用零补齐,valid 掩码把补出来的步从损失里剔除。归一化用 有效步数而不是补齐后的槽位数,否则补出来的零会把损失和梯度整体缩小, 且缩小比例随每批补齐多少而变。

2.3部署:C++ 侧只多两件事

rl_VG_v2.0/rl_VG.cpp 与 v1.0 那份的差别只有两处:

  1. 隐状态必须是全局的(g_h[128])—— 引擎每个阶段只调一次 act(),记忆要跨这些调用活下来才叫记忆;board.turn == 0 时与 g_ob/g_rules 一起归零。
  2. sigmoid 必须在 ±60 截断,与 Python 侧 _SIG_CLIP 一致 —— 不截断在 float32 下 exp(-x) 会在 x < −88 溢出成 inf。

头部另加 kRecurrent / kGruHidden 两行显式架构标记。 不靠"有没有 kGruHidden"去猜是刻意的:隐式约定少写一行就静默退化成纯 MLP, 而表现只是"发出去的包比测出来的弱"。

§3

验证:在没有 C++ 工具链的前提下

残留风险 · 本次交付最大的一个

本机没有任何 C++ 编译器(g++ / clang++ / cl / gcc / cc / tcc 全部不存在, msys64 / MinGW / LLVM 路径为空)。所以部署侧代码一次都没有被编译过。 上线前必须真编译一次 —— 这条建议写在 README §四。

补偿手段分两层,都在 tests/test_gru_deploy.py:

判据手段实测
A 前向把 rl_VG.cpp 的 forward 逐行转写成 Python,float64 对拍单步 9.1e−15
B 时序24 步连续传隐状态1.2e−14,全程一致
C 锚定_py_step 与 forward_seq 互相对拍(防"两个错的东西互相印证")1.3e−15
D 退化P=bP=0 时是否逐位等于纯编码器路径0.000e+00
E 端到端用真实导出包走 load_pack_net 解析路径16 步 6.2e−15
F 符号rl_VG.cpp 引用的每个 kXxx 都能在包里找到声明39 引用 / 57 声明,无未知
G 词法两条转写结构上表达不了的坑,直接查 C++ 文本见下

A~F 抓不到的,用 G 补。变异测试(对 C++ 文本做 5 种结构性改动,逐一确认测试变红) 暴露出两处numpy 转写结构上无法表达的危险:

  • h_prev 必须先存再写 h。反向里 dz = dh*(h_prev - n) 与三处 @ h_prev 都要用它。在 numpy 里 h = (1-z)*n + z*h_prev 是 重新绑定一个新数组,所以那个时刻 h 与 h_prev 的值相同, 写错也测不出来;C++ 里 h[i] = ... 是原地写,这个坑是真的。
  • sigmoid 截断。numpy 下输入到不了 ±60、float64 的 exp 也不会溢出, 所以删掉截断测不出来;float32 下它是必须的。

这两条各配一条词法测试(test_gru_step_reads_the_old_h_before_writing_the_new_one 按索引比较语句位置;test_sigmoid_clip_matches_the_python_one 用正则取数值再比较, 不比较格式)。三条 C++ 变异(挪 hprev 拷贝、把 60 改成 88、引用 kGruWHm) 现在全部被抓住。

仍然抓不到

语法错误、类型错误、#include 缺失、模板 / static_assert 问题。 上线前必须真编译一次。

§4

遇到的问题与解决方案

4.1只在交付时刻现形的坑(平时被跳过)

这两个都是测试自己的 bug,而且都因为"权重头不存在就跳过"而长期潜伏 —— 导出完成的那一刻才第一次运行:

  1. forward_seq 返回 (logits, values),不是隐状态。 我写成 lg_ref, h_py = net.forward_seq(...),把 values 接进了隐状态槽位, 报出"第 0 步隐状态分叉(最大差 1.606e+00)"。修法:加一个 _py_step(net, obs, h), 用公开 API 在 float64 下重写 RNNPolicy.step 的三步,并加一条断言把它锚回 forward_seq,防止"两个错的东西互相印证"。
  2. 同一个坑在打包后第二次踩。 test_deploy_forward_agrees_with_a_real_pack 里还留着旧写法,导出完成后立刻 ValueError: matmul ... size 128 is different from 1。 结论:跳过型测试在它第一次真正运行之前,不能算测试。 后来专门给它加了一句注释说明这个形状是从哪来的。

4.2静默变弱:gru → gru 续训会丢掉记忆

load_init_net 原来无条件走 RNNPolicy.from_mlp,而 from_mlp 只搬 _INHERITED 那 16 个张量 —— 拿 rl_VG_v2.0 当起点时,它会把 训好的 GRU 与 P/bP 丢掉、重新随机初始化,而打印出来的话术还是"初始前向逐位等于 rl_VG_v2.0"。形状全对、一处不报错,表现只是"续训了但没变强"。

  • 修法:检测到起点本身就是循环包时,按张量名整份 load_state_dict (30 个张量),顺带校验 hidden / gru_hidden 是否匹配(不匹配才报错);
  • 绊线:tests/test_train.py::test_init_pack_gru_to_gru_copies_the_memory_too, 断言 |bP|.max() > 0 且 20 步前向与包逐位一致。用真实包跑,所以同时覆盖 load_pack_net 解析 GRU 包那一段。

4.3包能被读 ≠ 包能被注册

RNNPolicy 没有 logits(obs) 方法(只有 step(obs, h)), 于是 LazyPackNet.logits() / test_pack.py 的注册表检查一遇到 GRU 包就 AttributeError。修法:补一个 logits(obs) = "零隐状态下的单步前向",并在文档里写清它的语义(它是"这一局刚开局、还没有任何历史"时网络 会说的话,不是"这个观测单独看"的答案);带记忆的调用方一律该用 step(obs, h)。

4.4注册一个包要三处齐全

加了 KNOWN_PACKS 却忘了 STATIC_OPPONENTS,训练在启动时抛 ValueError: 未知对手: rl_VG_v2.0。这是 README §七判据 F 记过的那类事故, test_pack.py 里有专门测试,但那次事故的教训不是"加个测试",而是 "加一个包 = KNOWN_PACKS 一行 + STATIC_OPPONENTS 一条,缺一不可"。

4.5读数依赖名单:evaluate() 只有一条采样流

evaluate() 全程共用一条 NetPolicy RNG 流, 按对手在字典里的顺序依次消耗。所以"某个对手的胜率"取决于它前面跑了多少局 —— 换名单、换顺序、换局数,读数就不可比。

本次实测到的后果很直观:同一个 v2.0 权重对 rl_v5 的读数

口径rl_v5
10 对手名单、40 局、seed 200.650✗ 流位置噪声
10 对手名单、40 局、训练器种子0.775✓
4 对手名单、200 局、seed 900000.765✓
单对手名单、400 局、seed 200.762✓

三个独立口径都落在 0.76~0.78,只有 seed-20 那条 10 对手流给出 0.650 —— 那是 40 局 (±0.079)在特定流位置上的噪声。纪律:报任何读数必须带名单 + 局数 + 种子。 tests/diag_one_opp.py 就是为此写的:单对手名单下那条流只服务一个人,读数最干净, 局数可以放心往上堆。

4.6评论腐化(定时任务发现的)

本轮审注释发现并修掉了四处与代码不符的注释:

位置原来的说法实际
env/rules_vg.py 模块 docstring "连续失明 2 个阶段" MISS_THRESHOLD = 4

这类注释比没有注释更坏:它们给的是具体而错误的信息,读者会照着它去理解代码。

4.7环境

  • Windows GBK:变异测试的 subprocess.run 抓 UnicodeDecodeError: 'gbk' codec can't decode byte 0xb4, 加 encoding="utf-8", errors="replace" 解决。
  • 日志缓冲:训练输出重定向到文件时,评测段落可能攒到下一次 8KB 刷新才出现, "看起来卡住了"不代表卡住。解决办法是盯 metrics.csv / best.npz 的 mtime,而不是盯日志 —— 那些是评测一结束就落盘的。
§5

负面发现:记忆的贡献落在噪声里

把包里 P / bP 强制归零(等价于"有记忆层但不用它",前向逐位退化成纯编码器), 在同一口径下重测:

对手带记忆P=bP=0差
rl_v50.7650.730+0.035
rl_VG_v0.20.9350.910+0.025
rl_best0400.9050.915−0.010
rl_VG_v1.00.9150.915+0.000
平均0.88000.8675+0.0125

记忆在表示上是实实在在工作着的 —— 实测 |P·h + bP| / |a3| 的平均比值是 0.29,也就是记忆那一支的尺度是编码器输出的三成,不是可以忽略的零头。但它在 胜率上的贡献只有 +0.0125 的平均值,4 个对手里 3 个略好、1 个持平,单格 ±1SE 是 0.035 —— 全部落在噪声里。

必须诚实地说

v2.0 相对 v1.0 的巨大提升(+0.385 vs v1.0)主要来自 "在含 rl_VG_v1.0 的联盟里继续训练"(联盟里它开局占 27.8% 的采样; league_weight_mode="room" 按"谁还有余量"动态配重,到 update 40 时它是 9.9%, 而 official_hunter 拿走了 24.8%),而不是来自记忆架构本身。

为什么记忆没长起来?当时最可疑的解释是优化压力不够:P 从零出发, 而它前面站着的是一个已经很强的编码器,把 P 推大的边际收益很小;同时 lr(3e-4)是给一个 全新网络调的,对"只微调一小块新增参数"这件事偏大 —— 这也解释了早期那次全面回撤。

这个猜测已经被 runs/v2.1 否证 —— 见 §6。结论是:不是"还没训够", 而是这个架构 + 这套优化目标下,记忆支就长不到有正贡献的规模。

这条发现不改变交付结论(目标读数四个全过线,且是两个独立种子各 200 局实测), 但它改变了对成绩的归因,而这正是探索报告该说清楚的事。

§6

v2.1:多训 2.4 倍步数,记忆反而缩了

6.1这一轮想验证什么

§5 的猜测是"记忆没长起来 = 优化压力不够"。要是这个解释成立,那就该:让起点更强 (从 v2.0 整份继承,而不是从零开始)、把学习率降下来(3e-4 → 1.5e-4, 别让新增的小参数被大步长推飞)、给它更长的生长时间(400k 步,不早停)。三条一起上。

配置(runs/v2.1/final.npz 的 meta 实录):

--run-name v2.1 --arch gru --gru-hidden 128 \
--init-pack rl_VG_v2.0 --lr 1.5e-4 --steps 400000     # 不设 --stop-opponents
联盟(9):official_baseline/hunter/stalker/patrol, rl_v5, rl_VG_v0.2,
        rl_best040, rl_VG_v1.0, rl_VG_v2.0            # 把 v2.0 本体也放进陪练

启动日志确认起点正确:架构 gru:整份继承 30 个张量(编码器 + 三个头 + GRU + P/bP) —— 初始前向逐位等于 rl_VG_v2.0。实际跑了 98 个 update / 401408 步 (是 v2.0 的 2.45 倍)。

消融(P=bP=0)的胜率贡献 +0.0125−0.0138 变大✗ 转负
综合(4 对手 ×200 局 ×seed 90000) 0.88000.8600 变大✗ 变低

v2.1 在四个目标上仍然全过线(rl_v5 0.770、v0.2 0.890、 best040 0.820、v1.0 0.960),所以它不是一次失败的训练 —— 它是"继续训下去并不能让记忆长起来"这个结论的证据。多花 2.4 倍步数,记忆那一支的尺度 没变大反而缩小了。

读数纪律

消融的两个数(+0.0125 / −0.0138)单格 ±1SE 都是 0.035,所以诚实的说法是 "记忆支没有正贡献",不是"它有负贡献"。两个符号相反、量级相当的读数合起来 说明的就这一件事:它对胜率的影响小于测量分辨率。

6.3结论:保留 rl_VG_v2.0

  1. 不打包 v2.1。命名规则是"一次训练一个小版本",v2.1 这次训练已经跑完、 权重留在 runs/v2.1/final.npz,但它的战绩没有超过 v2.0, 再冻结一个包只会让"用哪个"变模糊。
  2. §5 的解释被替换。不是"训练不够久",而是在"编码器已经很强 + 记忆做成零初始化 残差"这个组合下,P 的梯度信号始终不足以把它推到一个对胜率有用的规模。要验证 "记忆到底能不能帮上忙",得换一个更能逼出记忆的任务/对手设置 (例如对手带更强隐式状态、或者把部分观测做得更残缺),而不是继续加步数。
  3. rl_VG_v2.0 的交付结论不受影响 —— 它是两个独立种子上都四个目标全过线的那一份。

6.4一个顺带观察(未深入)

v2.1 在不在联盟里的 m3_v1 上从 0.675 掉到 0.250 (训练器自己的 10 对手评测)。m3_v1 / m3_v2 都不在 v2.1 的 9 个陪练里, 是纯泛化探针。训得越久、越贴合这个联盟,对联盟外对手的棋力退化越明显 —— 这是联盟训练的普遍现象, 与记忆架构无关,记在这里是因为它解释了"为什么综合没涨而单项有涨有跌"。

7.3⚠️ 这不能算推翻 §6

§6 的结论是"再多训 2.4 倍步数没用",而 v2.3 恰好也训了 2.45 倍并且涨了。看着矛盾,其实不是 —— v2.3 一次改了三件事,什么都没隔离出来:

  1. 起点谱系不同。v2.1 是 --init-pack rl_VG_v2.0,继承的是 v2.0 的整份权重 —— 连已经训过的 GRU 和尺度 0.29 的 P 一起 接着练;v2.3 是 --init-pack rl_VG_v1.0,只继承编码器与三个头, GRU 与 P/bP 全部从零开始。
    更正

    这条原先写的是"v2.1 踩了 §4.2 那个 gru→gru 静默丢记忆的坑"。那条是错的。 §6.1 引的启动日志是"整份继承 30 个张量……",而这句话只有修复后的 gru→gru 分支才会打印(selfplay.py:956;坏路径打的是"已继承编码器与三个头 (16 个张量)")。train_v2.1.log 已经不在了,无法再核,但两条陈述不能同时成立 —— 以日志文案为准:v2.1 走的是一条已经修好的续训路径,它记忆没长起来 跟 §4.2 无关。"起点谱系不同"这个混淆项本身照样成立,只是理由要换成上面这句。

  2. 联盟更宽。8 → 10 个陪练(多两个官方 AI)。
  3. 步数更多。163840 → 401408。
所以 v2.3 证明的是什么

"在 v2.0 的配置下把预算跑完能得到更强的策略",不是 "记忆这次长起来了"。§5.1 那个"GRU vs 同步数 MLP"的对照在 v2.3 上没有重跑, 所以它的结论(同步数下 GRU 0.768 vs MLP 0.700)对 v2.3 仍然只是外推。

要干净地分开这三件事,得跑同一份 v2.0 起点、同一张窄联盟、只把 stop_opponents 摘掉。这一轮没跑。

但 +0.0250 还不足以把结论翻过来

分辨率。n=200 的单格二项 ±1SE 在 p≈0.95 时是 0.015、p≈0.78 时是 0.029(§5 / §6.2 引的 0.035 是 p=0.5 的最坏值);4 格平均在 0.01 量级。+0.0250 大致 1.5~2.5SE —— 它是三个消融里第一个符号朝正的,不是第一个 显著的。

归零 P 不只是"撤掉信息"。v2.3 的 P 支尺度 是 0.47,归零等于把三个头的输入整体挪了一截。消融组变弱不能全算在"少了记忆"头上 —— 这条对 v2.0 / v2.1 同样成立,不是新问题,但它决定了这个差值不能当"记忆的贡献"读。

它不隔离 §7.3 那三件事。消融回答的是"训好的 v2.3 里那一支有多大用", 不回答"多训的 2.45 倍里有多少是记忆带来的" —— 那仍然只有 §5.1 的 MLP 对照能回答, 而 v2.3 上没有重跑。
